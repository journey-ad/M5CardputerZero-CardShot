# CardShot 可行性分析

面向 M5Stack Cardputer Zero（aarch64 Linux、320×170 RGB565 帧缓冲、实体键盘）的截图、截屏与录屏工具。

## 1. 目标与约束

- 常驻后台，随时抓取当前任何前台应用的画面
- 交互适配 320×170 小屏与 32 键实体键盘
- 附带相册管理（浏览、预览、删除）与远程 Web 管理（预览、下载、删除、设置）
- 后台常驻，内存占用尽量小

## 2. 取画面的可行性

设备只有一个全局帧缓冲 `/dev/fb0`（`/dev/fb_lcd`），320×170、RGB565 LE、行长 640、单帧 108800 字节。前台应用（CardBili、APPLaunch 等）都直接往这块缓冲写，因此后台进程只需 `pread` 整帧即可拿到屏幕内容，与被抓取的应用无关，无需其配合。

实测：连续 20 次 `pread` 仅耗 0.001s，读帧开销可忽略。抓取 CardBili 播放中的视频画面帧，相邻帧差异 5 万像素以上，确认拿到的是实时画面。

结论：后台抓屏完全可行，且天然支持「截取任意前台应用」。

## 3. 截图可行性

整帧拿到后可交给 `image`（Rust）编码为 PNG / JPEG / WebP，质量可配。实测三种格式与质量均生效：

- PNG 约 63 KB
- JPEG q60 约 18.7 KB
- WebP q40 约 12.3 KB

同一帧不同格式体积差异明显，格式与质量设置对存储占用影响大，适合暴露为可配置项。

## 4. 录屏可行性

设备有硬件编码器 `h264_v4l2m2m`，也有 `libx264` 软编。方式是把帧缓冲按 `rgb565le` 原始帧管道喂给 ffmpeg，编码为 H.264 MP4。

实测与问题：

- 早期硬件编码 60 帧 @20fps 用时 3.32s，子进程 CPU 1.39s，码率约 184 kbps；后来 `h264_v4l2m2m` 出现卡死（编码线程停在 futex，输出 0 字节），且 ffmpeg 卡住会让喂帧线程的 `stdin.write_all` 阻塞、停止操作永久挂起
- 改用 `libx264 -preset ultrafast -tune zerolatency`：编码 60 帧 320×170 @20fps 仅 1258ms（约 47fps），余量充足，现为默认编码器
- 修复喂帧节奏：开始录制时先预滚一帧穿过初始化，之后每写一帧固定 sleep 一个帧间隔，不做追赶
- 录制上限由 `record.max_seconds` 控制，默认 120 秒，超时自动停止并落盘
- 录制声音（默认内录）：音频源默认 `@DEFAULT_MONITOR@`（扬声器回环），视频与音频分开录制（`ffmpeg -f pulse -i @DEFAULT_MONITOR@ -ar 48000 -ac 2 -c:a pcm_s16le`），停止后合成 H.264+AAC；音频失败时保留无声视频并在状态里给出提示。实测播放 440Hz 音调录制：mean -16.9dB / max -8.8dB，确认为内录
- 实测 4 秒上限：录制在 4 秒结束，文件时长 3.93s，音视频正常

结论：设备以 libx264 软编可稳定支撑 320×170 常驻录屏，CPU 与内存余量充足；硬件编码在当前内核与管道模型下不可靠，仅作可选项。

## 5. 常驻内存评估与语言选型

后台常驻对内存敏感，分别实测两种实现：

| 实现 | 运行内存 | 体积 |
| --- | --- | --- |
| Python（Pillow + 本项目模块） | RSS 约 23 MB（PSS 18 MB） | 代码 268 KB，但依赖 Python3.13 stdlib 约 53 MB + 解释器 6.7 MB + Pillow 3.1 MB |
| Rust（静态链接） | RSS 约 2.5 MB | 单二进制约 1.2 MB，无运行时依赖 |

Python 版即便功能正常，运行时基线也达 23 MB 量级；Rust 版约 2.5 MB，是前者的十分之一量级，且打包为单文件自包含。参照同机 CardBili（Rust+Slint）运行 RSS 约 4.1 MB、二进制 21.6 MB（含字体），说明该技术栈在设备上成熟可用。

结论：为满足小内存常驻目标，采用 Rust 实现守护进程与设备端界面。

## 6. 交互设计（小屏 + 实体键盘）

屏幕仅 320×170，键盘为 32 键（方向键映射在 Z/X/C/F 等物理键上），因此：

- 不做多窗口，采用整屏分页：主页 → 相册 → 预览 / 设置，`Esc` 逐级返回
- 不使用鼠标语义，全部用方向键移动焦点、`Enter` 确认、`Space` 多选、`退格` 删除（二次确认）、`Shift+退格` 直接删除
- 后台守护负责抓屏/录制，设备端界面只做相册管理，不放置截图/录制入口，避免把「常驻服务」误当成「前台工具」
- 全局热键（组合键）作为免开界面的快捷入口，默认开启，可在设置里配置截图快捷键
- 组合键与前台应用可能存在冲突，实践中通过可配置 + ACT LED 闪烁反馈降低误触与不确定感
- 界面以功能布局本身表达操作：主页卡片带图标与计数，缩略图角标用图标区分图片/视频，视频中心为圆圈三角播放标记，方向切换用三角箭头；按键细节收进「使用说明」弹窗，不在界面堆砌文字

## 7. 远程 Web 管理

守护内置 HTTP 服务（默认端口 8420，可配置），提供与设备端一致的能力：状态、列表、缩略图、文件下载（支持 Range，可拖动播放）、截图、录制、删除、配置、远程开关。前端为单页应用（Preact + htm，无构建步骤），桌面/手机浏览器均可使用。局域网内以设备 IP 访问即可。

## 8. 风险与限制

- 仅能抓取 RGB565 帧缓冲内容，无法获取叠加层之外的 GPU 图层（本设备为软件渲染，实际无影响）
- 录屏默认不含音频，音频采集需另行接入
- 硬件编码初始化有秒级延迟，首次录制开头需预滚处理
- 帧缓冲是 RGB565（r5/g6/b5）；ffmpeg 输入须为 `rgb565le`。早期误用 `bgr565le` 造成录制与 WebP 红蓝互换，已修正并用三色测试图逐像素验证（截图为正确 RGB）
- 全局热键为轮询键盘事件，可能与前台应用争用同一组合键
- Web 管理默认监听 0.0.0.0，需在可信局域网内使用；可配置端口与开关

## 9. 结论

后台抓屏、三种格式截图、硬件编码录屏、常驻低内存、小屏键盘交互、远程 Web 管理均已在本机实测可行，并已落地为 Rust 守护 + Rust/Slint 设备界面 + Web 管理页的实现。

## 10. APPLaunch 集成与打包

界面按 CardBili 的约定集成到 APPLaunch：

- 桌面入口 `/usr/share/APPLaunch/applications/cardshot.desktop`，`Terminal=false`，`Exec` 指向包装脚本 `run-cardshot`
- 包装脚本设置 `XDG_RUNTIME_DIR=/run/user/1000` 后启动 `/usr/share/APPLaunch/bin/cardshot-ui`，保证与以用户服务运行的守护共用控制 socket
- 图标 `share/images/cardshot_100.png`（100px 桌面）与 `cardshot_256.png`（256px 商店/详情），由 `cardputer-zero-application` 技能脚本生成
- 图标素材取自 Pixelarticons（MIT），应用内缩略图角标、播放标记、方向箭头均为同库 SVG，由 Slint 原生渲染，不做 PNG 转换
- 字体沿用 CardBili 的 Fusion Pixel 预光栅化管线（`build/font_cache.rs` + `build/ui_fonts.rs`），界面文字无额外运行时依赖

安装：`bash scripts/install-app.sh`（写入 APPLaunch 目录并重启 APPLaunch 用户服务）。
